# Changes made for portable verification

The original mathematical source bodies are retained beside the portable
checkers and bound by their source maps. The adaptations provide explicit
input roots, fresh execution records and a usable recipient interface.
They do not turn historical success flags into fresh verification.

The numerical scheduling change lets one authenticated numerical controller
continue through its existing finite retry ladder when a count returns a
usable partial result. It preserves successful individual counts, all source
checks, the original cumulative budget and the 120-second child deadline.
Missing evidence, a mismatch, an unusable result or a mandatory hold still
stops that continuation. Each fresh recipient workspace records its actual
driver version and requires explicit finite job and time allowances.

The acceptance reader recognizes that exact new driver version only with its
own fresh recipe. The mathematical acceptance predicates are unchanged. The
recipient entrypoint passes the already frozen numerical allocation to the
scheduling call; repeated calls retain the original cumulative child budget.

The exact earlier numerical driver, acceptance source and entrypoint are in
`adaptations/scheduling-001/`. That directory also contains the complete
source-construction record and the one-line entrypoint diff. These files
document source changes; completed verification is reported separately in
[REPLAY.json](../REPLAY.json).

A further correction handles a final-rung count that was shortened because
earlier sites consumed the shared child allowance. Continuation at the same
final-rung caps requires an authenticated partial result with newly completed
sites and an exact smaller pending set. Every remaining site must have a
time refusal demonstrably below its nominal allowance. No progress, another
refusal type, full per-node exhaustion or an adverse observation stops this
continuation. Pending cardinality decreases, and all existing cumulative and
per-child limits remain in force. The earlier driver and acceptance versions
and the exact source record are retained in `adaptations/final-rung-001/`.

The recipient interface also accepts up to 4,096 jobs in a bounded controller
call. This changes the batching ceiling and its help text; each underlying
controller keeps its deadlines, source checks, finite roster, cumulative
allocations and adverse-result stops. Earlier interface sources and the exact
three-line diff are retained in `adaptations/batch-size-001/`.

## Final metadata assembly

The final exact union check authenticates completed terminal executions and
their input files. The full 85-part union exceeded its initial 100-second
allowance. A separate finite 600-second internal / 660-second physical limit
now applies to assembly; individual counting and terminal-verification children
retain their existing limits. The entrypoint's prior source and one-line
scheduling change are preserved in `adaptations/assembly-time-001/`.
No completeness or mathematical acceptance predicate changes.

Final composition also receives the exact compiler path already frozen by the
entrypoint. This lets the final evidence check admit that single tool, together
with its existing exact Python and source-root bindings. The prior entrypoint
and its one-line argument change are preserved in
`adaptations/compiler-finalize-001/`. The command adds no general external
directory and changes no count or coefficient predicate.

The U11 reader now uses the compact records' actual `group_id` field and rejects
missing or conflicting identity aliases. Its complete 495-row bridge and all
triple, degree, geometry, count and sign predicates remain in place. The prior
source and exact change are retained in `adaptations/u11-and-assembly-001/`.

The final source set in `adaptations/metadata-final-001/` records the remaining
operational changes. Assembly and composition use local caches for repeated
evidence paths. Each row still checks its exact evidence hashes; first-use
admission and the original final source checks remain. This removes millions
of redundant filesystem operations without changing the complete identity union.

`composition_metadata.py` provides a separate, source-bound invocation for
the final acceptance and composition phases. It retains the immutable core
files, records each exact function adaptation and uses 600-second internal,
660-second child and 900-second launcher limits for those metadata phases.
Earlier scientific phases retain their original launcher and limits. The
new source set was exercised by targeted fixtures with actual isolated child
processes; `REPLAY.json` states the separate scopes of full export verification
and recipient-interface tests.
